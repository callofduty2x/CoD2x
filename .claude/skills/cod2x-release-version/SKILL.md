# CoD2x release commit ("Version x.x.x.x")

A release is **one source-only commit that bumps the version**, followed by **a `v<ver>` tag that
CI turns into the GitHub Release**. Features and fixes land earlier in their own commits
(`Console: ...`, `New cvar ...`, `Docker: ...`). The version commit only bumps the number and
updates the README; it ships no binaries.

Binaries, symbol headers and zips are **not committed** - they are gitignored and built by CI from
the tag (`.github/workflows/release.yml` -> `build.yml` -> `.github/scripts/package.sh`), then
attached to the GitHub Release. The "Version ..." commit itself does **not** release; only the tag does.

## 1. Pick the version number

Format `a.b.c.d[-test.N]` - defined in [makefile](../../../makefile) (top of file):

| Part | Variable | Rule |
|---|---|---|
| a.b | `VERSION_MAJOR`, `VERSION_MINOR` | always `1.4` |
| c | `VERSION_PROTOCOL` | +1 only when client and server must both update (old client cannot join new server). Resets patch to `1`. |
| d | `VERSION_PATCH` | +1 for every backward-compatible release |
| -test.N | `VERSION_TEST`, `VERSION_IS_TEST` | test builds: `VERSION_TEST = -test.N`, `VERSION_IS_TEST = 1` |

Sequences seen in history:
- normal patch: `1.4.6.7` -> `1.4.6.8`
- test series: `1.4.4.6` -> `1.4.5.1-test.1` ... `-test.13` (test number +1 each time, base stays)
- leaving a test series: either the same base (`1.4.3.2-test.2` -> `1.4.3.2`) or, if protocol
  changed again, the next protocol (`1.4.5.1-test.13` -> `1.4.6.1`). Final release sets
  `VERSION_TEST =` (empty) and `VERSION_IS_TEST = 0`.

If the protocol changes, check code that switches on the protocol version (e.g. `FS_iwIwd` in
`src/shared/iwd.cpp` switches on `cod2x_version`) and add the new value there - that edit
belongs in the version commit (see 1.4.6.1).

Ask the user if it is unclear whether the release is protocol-breaking or a test build.

## 2. Files the commit must contain

Edit **only the makefile by hand**; version.h and version.rc are generated. The commit is source-only.

| File | How it changes |
|---|---|
| `makefile` | the version variables above |
| `src/shared/version.h` | regenerated by `prebuild` from the makefile - never edit by hand |
| `src/mss32/version.rc` | regenerated by `prebuild` (`FILEVERSION`, `PRODUCTVERSION`, `ProductVersion`) |
| `README.md` | see section 4 |

Do **not** commit (all gitignored, built by CI): `bin/windows/mss32.dll`, `bin/linux/libCoD2x.so`,
`src/mss32/symbols_mss32.h`, `src/linux/symbols_libcod2x.h`, `zip/**/*.zip`. The
`CoD2x Installation and uninstallation manual.txt` files in `zip/*` stay committed (CI puts them in
the archive). Images under `images/` may be included only when a README section that references them changed.

## 3. Prepare and publish

1. Edit the makefile version variables.
2. Regenerate the version files: **`mingw32-make prebuild`** (updates `version.h` + `version.rc`).
   No full build is needed for the commit - CI builds the binaries.
3. *(Optional)* sanity-build locally to confirm it still compiles - VS Code tasks
   **Rebuild Win RELEASE** / **Rebuild Linux RELEASE** (`DEBUG=0`). Nothing from the build is committed.
4. Update the README (section 4).
5. Commit `Version <ver>` (section 5) and push to `main`.
6. **Publish the release** - push the tag:
   ```
   git tag v<ver>
   git push origin v<ver>
   ```
   CI (`release.yml`) builds Windows + Linux through the shared pipeline, zips them, and creates the
   GitHub Release with the binaries + zips attached. A `-test.N` tag becomes a GitHub **pre-release**.
   CI fails the publish if the tag does not match the makefile version (`make print-version`), so keep
   them in sync.

## 4. README.md edits

### Version history (top of file)
Final release - move the previous "current" into the `<details>` list and add the new one.
Note the separators: current line uses ` - `, older lines use `:`.

```markdown
# Version history
- YYYY-MM-DD - **[1.4.6.9](https://github.com/callofduty2x/CoD2x/releases/tag/v1.4.6.9)** - **current**

<details>
  <summary>Older versions</summary>

- YYYY-MM-DD: **[1.4.6.8](https://github.com/callofduty2x/CoD2x/releases/tag/v1.4.6.8)**
- ...
```

Test build - a line above the current release, no link (there is no GitHub release for it),
and it is replaced (not stacked) on the next test build:

```markdown
- YYYY-MM-DD - 1.4.5.1-test.13 - *current testing*
- YYYY-MM-DD - **[1.4.4.6](...)** - **current**
```

The date is the release date (the day of the commit), not the date of the last feature.

### Download links
Final releases only - update both install sections, version appears 3 times in each link:
- `# How to install (client on Windows)` -> `CoD2x_<ver>_windows.zip`
- `# How to install (server on Linux)` -> `CoD2x_<ver>_linux.zip`

`https://github.com/eyza-cod2/CoD2x/releases/download/v<ver>/CoD2x_<ver>_<platform>.zip`

Test builds do not touch the download links.

### Feature list
`# Features` (`#### Changes`, `#### Improvements`) and `# GSC functions` should already be updated
by the feature commits. In the version commit, go through `git log --oneline <last Version commit>..HEAD`
and add or fix any README entry that a feature commit missed (renamed/removed cvars, new commands,
new cvars). Describe the user-visible behaviour, one bullet per feature, cvars and commands in
backticks, sub-options as nested bullets - same style as the existing list.

## 5. Commit and tag

- Message: exactly `Version 1.4.6.9` or `Version 1.4.5.1-test.13` - no body, no other text.
- Stage source only: `makefile`, `src/shared/version.h`, `src/mss32/version.rc`, `README.md`.
  Verify with `git status` that no binaries, symbol headers or zips appear (they are gitignored).
- Do not mix source changes (other than the protocol switch from section 1) into this commit.
  If there are uncommitted feature changes, commit them first as their own commit.
- Only commit when the user asks. The release is published by pushing the `v<ver>` tag (section 3,
  step 6) - the user does the push unless they ask otherwise. The commit alone does not release.

## Checklist

- [ ] makefile version bumped correctly (patch / protocol / test)
- [ ] version.h and version.rc regenerated (`make prebuild`) and show the new version
- [ ] README: version history, download links (final only), feature list complete
- [ ] commit message `Version <ver>`, source-only, nothing unrelated and no build artifacts
- [ ] tag `v<ver>` pushed so CI builds and publishes the GitHub Release (tag must match `make print-version`)
